# ROADMAP — план разработки Scenarist

Результаты полного ревью кодовой базы (версия 0.4.11, июнь 2026).
Пункты упорядочены по важности: сначала баги, угрожающие данным пользователя,
затем надёжность, производительность, i18n, качество кода и гигиена проекта.

Статусы: `[ ]` — не начато, `[~]` — в работе, `[x]` — готово.

## P0 — Критичные баги (целостность данных)

Эти баги способны испортить или потерять данные пользователя. Чинить в первую очередь,
каждый фикс сопровождать тестом в `tests/`.

### 1. `[x]` Vault-события не фильтруются по расширению → `.sc`-файлы портят `filePath`

**Где:** `src/sync/SyncEngine.ts` — `handleCreate` (≈246), `processCreatedFile` (≈335), `handleModify` (≈202).

**Проблема.** `store.save()` пишет sidecar `x.sc` через `adapter.write` → vault бросает
событие `create` → `handleCreate` → `processCreatedFile("x.sc")` → `readSidecar("x.sc")`
читает **сам себя** (регексп `/\.md$/` в `sidecarPath` не матчится на `.sc`, путь не меняется) →
entity найдена по id → `existing.filePath ("x.md") !== file.path ("x.sc")` →
`setFilePath(id, "x.sc")`. Результат: карточка рендерит JSON как markdown,
`syncToNote` целится в `.sc`, `byPathIndex` указывает на sidecar. Само-чинится
только следующим `rescanVault`.

**Решение.**
- В начале `handleCreate`, `handleModify` (и для надёжности `handleRename`) — ранний выход,
  если `file.extension !== 'md'` (rename .sc обрабатывается отдельно внутри `handleRename` .md).
- В `sidecarPath` добавить защиту: если путь уже оканчивается на `.sc` — вернуть как есть/бросить.

**Критерий готовности:** тест — эмуляция `create`-события для `.sc`-файла не меняет
`filePath` сущности.

### 2. `[x]` Переименование сущности создаёт дубликат заметки

**Где:** `src/models/ScenaristStore.ts` — `rename` (≈177); `src/sync/SyncEngine.ts` — `ensureNote` (≈105), `buildPath` (≈75).

**Проблема.** `rename()` меняет только `entity.name`. Путь заметки строится от имени,
поэтому следующий `ensureNote`/`openNote` построит новый путь, не найдёт там файл и
**создаст второй .md** (и второй .sc). Старый файл останется с тем же `scenarist_id` —
при `rescanVault` старый и новый файлы будут «перетягивать» `filePath` друг у друга.
Для `project`/`work`/`category` имя входит и в пути **дочерних** сущностей — после
переименования контейнера все дети будут пересозданы в новой папке при следующем `ensureNote`.

**Решение.**
- Новый метод `SyncEngine.renameEntity(id, newName)`:
  1. `store.rename(id, newName)`;
  2. если файл существует — `app.fileManager.renameFile(file, newPath)`
     (это сохранит и обновит wikilinks в vault); `handleRename` уже переносит sidecar;
  3. для `project`/`work`/`category` — переименовать папку
     (`fileManager.renameFile` на TFolder) вместо пофайлового переноса;
  4. `setFilePath` для всех затронутых сущностей.
- В `CardView` (title.onchange, ≈207) звать `renameEntity` вместо `store.rename + syncToNote`.

**Критерий готовности:** тест — rename сущности с заметкой не создаёт второй файл;
rename work переносит папку с главами.

### 3. `[x]` `deleteEntity` не удаляет sidecar → удалённые сущности «воскресают»

**Где:** `src/sync/SyncEngine.ts` — `deleteEntity` (≈178).

**Проблема.** В корзину отправляется только `.md`. Осиротевший `.sc` остаётся в vault;
если пользователь его откроет — `EntityFileView.onLoadFile` сделает `importEntity` и
вернёт удалённую сущность в Store.

**Решение.** В цикле удаления для каждого `e.filePath` также трэшить
`store.sidecarPath(e.filePath)`, если файл существует.

**Критерий готовности:** тест — после `deleteEntity` ни `.md`, ни `.sc` не существуют.

### 4. `[x]` Реципрокность игнорирует `single` на обратной стороне

**Где:** `src/models/ScenaristStore.ts` — `addReverse` (≈226), `setLink` (≈206).

**Проблема.** `addReverse` просто добавляет id в массив. Если главу добавить в
`chapters` двух книг, у главы получится `book: [A, B]`, хотя `LinkDef.book.single === true`.
`ownerWork`/`parentOf` берут первый элемент — пути файлов и хлебные крошки становятся
непредсказуемыми.

**Решение.** В `addReverse` находить `LinkDef` обратной связи (через `findLinkDef`
по целевой сущности); если `single` — перед добавлением **снять** прежнюю связь у
старого владельца (полная реципрокная очистка: у старой книги удалить главу из `chapters`).

**Критерий готовности:** тест — перенос главы из книги A в книгу B оставляет
`chapter.book === [B]` и убирает главу из `A.chapters`.

### 5. `[x]` `selfWrites` может навсегда «съесть» правку пользователя

**Где:** `src/sync/SyncEngine.ts` — `selfWrites` (≈19), `syncToNote` (≈134), `handleModify` (≈204).

**Проблема.** Запись снимается из Set только следующим modify-событием. Если
`processFrontMatter` ничего не изменил (frontmatter уже актуален — события нет),
путь висит в Set вечно, и первая настоящая правка пользователя в этом файле будет
молча проигнорирована.

**Решение.** Заменить `Set<string>` на `Map<string, number>` (path → timestamp записи).
В `handleModify` игнорировать событие, только если запись была < ~1500 мс назад;
запись из Map удалять в любом случае.

**Критерий готовности:** тест — modify-событие через 2 с после `syncToNote`
обрабатывается как пользовательская правка.

### 6. `[x]` Удаление без подтверждения

**Где:** `src/views/NavigatorView.ts` — `contextMenu` (≈547).

**Проблема.** Один пункт контекстного меню сразу удаляет сущность + её файл, а для
категории — каскадно все элементы с файлами. Промахнуться очень легко.

**Решение.** Confirm-модал (стандартный паттерн: `Modal` с кнопками «Удалить» /
«Отмена», warning-стиль). Для категории в тексте указать количество удаляемых
элементов. Упомянуть, что файлы уезжают в корзину (восстановимо), — но Store-данные
теряются безвозвратно, поэтому подтверждение обязательно.

## P1 — Надёжность и неожиданные побочные эффекты

### 7. `[x]` Просмотр карточки мутирует файл (авто-коммит дефолтов select/status)

**Где:** `src/views/CardView.ts` — `renderFieldControl` (≈461): `queueMicrotask(() => this.commitProp(...))`.

**Проблема.** Открытие карточки с пустым required-полем записывает дефолт в Store и
frontmatter. Просмотр не должен менять данные (меняет `updatedAt`, трогает файл,
генерит события синхронизации).

**Решение.** Показывать дефолт визуально (selected option), но коммитить только при
реальном `onchange`. Дефолт записывать в момент **создания** сущности
(в `CreateEntityModal` это уже происходит для required-полей).

### 8. `[x]` Правки связей во frontmatter теряются

**Где:** `src/sync/SyncEngine.ts` — `handleModify` (≈202).

**Проблема.** Обратная синхронизация читает только поля-props. Если пользователь
отредактировал wikilink-связь в frontmatter руками, Store об этом не узнает, и
следующий `syncToNote` молча перезапишет правку.

**Решение (вариант A, проще).** Честно объявить frontmatter-связи read-only:
при `handleModify` сравнивать связи и, если разошлись, восстанавливать их из Store
(+ Notice «связи редактируются в карточке»).
**Решение (вариант B, полноценное).** Парсить wikilinks из frontmatter, резолвить
имена → id (через byKind + имя), вызывать `setLink`. Неоднозначные имена — пропускать.
Начать с A, B — отдельной задачей.

### 9. `[x]` Коллизии имён в `buildPath`

**Где:** `src/sync/SyncEngine.ts` — `buildPath` (≈75), `ensureNote` (≈105).

**Проблема.** Две сущности с одинаковым именем в одной папке получают один путь:
`byPathIndex` хранит только одну, `ensureNote` привяжет обе к одному файлу,
`syncToNote` будет перезаписывать frontmatter то одной, то другой.

**Решение.** В `ensureNote` перед созданием: если путь занят файлом **другой**
сущности (`findByPath(path)?.id !== entity.id`) — добавлять суффикс ` (2)`, ` (3)`…
до свободного пути.

### 10. `[x]` Импорт `.sc` без валидации

**Где:** `src/views/CardView.ts` — `EntityFileView.onLoadFile` (≈989): `importEntity(data as any)`.

**Проблема.** Открытие битого/чужого `.sc` инжектит произвольный объект в Store
(затем он попадёт в индекс и обратно на диск).

**Решение.** Функция-гард `isValidEntity(data): data is Entity` в `models/types.ts`
(проверка `id: string`, `kind ∈ KINDS`, `name: string`, `props/links — объекты`).
Применить в `onLoadFile` и `rescanVault`/`processCreatedFile` (ветка sidecar).
Невалидный файл — Notice + пустая карточка.

### 11. `[x]` `INDEX_VERSION` пишется, но не проверяется

**Где:** `src/models/ScenaristStore.ts` — `load` (≈336), `src/models/types.ts` (INDEX_VERSION = 2).

**Решение.** При `load()` читать `data.version`; завести `migrateIndex(data)` с
последовательными шагами `v1→v2→…`. Сейчас шагов нет — но каркас нужен до того,
как формат снова поменяется. Версию > текущей — не грузить (Notice о downgrade).

### 12. `[x]` `flushSave` не делает то, что обещает

**Где:** `src/state/ScenaristState.ts` — `flushSave` (≈62).

**Проблема.** Комментарий: «немедленно сохраняем settings без debounce», код — только
отменяет таймер. Работает лишь потому, что `onunload` следом зовёт `saveSettings()`.

**Решение.** Либо реально вызывать `void this.plugin.saveSettings()` если таймер был
активен, либо переименовать в `cancelPendingSave` и поправить комментарий + CLAUDE.md.

## P2 — Производительность (деградирует с ростом vault)

### 13. `[x]` `save()` переписывает ВСЕ sidecar-файлы при каждом сохранении

**Где:** `src/models/ScenaristStore.ts` — `save` (≈397).

**Проблема.** Каждый debounce-тик = запись индекса + N записей `.sc` (при 500
сущностях — 500 файловых операций на любое изменение одного поля). Каждая запись
ещё и генерит vault-события (см. п. 1).

**Решение.** Dirty-set: `private dirtyIds = new Set<string>()`; все мутации добавляют
id; `save()` пишет sidecar только для dirty и очищает set. Полная перезапись —
только по явному действию (миграция, rescan).

### 14. `[x]` `refreshViews()` зовёт `store.save()` в обход debounce

**Где:** `src/main.ts` — `refreshViews` (≈202).

**Решение.** Убрать прямой `save()` — мутации Store уже планируют `scheduleSave`.
Если где-то `refreshViews` вызывался ради сохранения без мутации — заменить на
явный `store.save()` в том месте.

### 15. `[x]` Полная перерисовка всех вью на каждый `notify()`

**Где:** все `views/*` (`onChange(() => this.render())`), особенно:
- `GraphView.render` — 250 итераций O(N²) симуляции на каждое изменение + сброс
  позиций, которые пользователь растащил мышкой (`GraphView.ts` ≈141);
- `NavigatorView.render` — полная перестройка дерева на каждый **символ** в поиске,
  с хаком восстановления фокуса (`NavigatorView.ts` ≈103).

**Решение.**
- Debounce рендера (~50–100 мс) в базовом подписчике всех вью.
- GraphView: кэшировать позиции узлов по id между рендерами; пересчитывать layout
  только при изменении состава узлов/рёбер; обновление выделения — без пересимуляции.
- NavigatorView: debounce инпута поиска (~150 мс); в перспективе — точечное
  обновление DOM вместо `empty()` + rebuild.

### 16. `[x]` GraphView: слушатель `mousemove` на svg для каждого узла

**Где:** `src/views/GraphView.ts` — `renderNode` (≈216–233).

**Решение.** Один `mousemove`/`mouseup` на svg + переменная «текущий перетаскиваемый
узел», `mousedown` на узле только назначает её.

## P3 — i18n: добить вторую локаль

Решение «stored values не переводятся» — осознанное и остаётся в силе.
Но UI-тексты и инфраструктурные строки не должны быть захардкожены по-русски:

### 17. `[x]` Русские строки вне i18n

- `CHAR_ROLES = ['Главная', …]` — `src/views/NavigatorView.ts:13`. Это **значения**
  `props.role` (не переводим как данные), но они же показываются как заголовки групп.
  Решение: брать роли из `SCHEMAS.character` (options поля `role`), а заголовок группы
  рендерить через карту value → ключ перевода.
- `'_Без проекта'`, `'Без имени'`, `'_Без произведения'`, `'Категория'` —
  `src/sync/SyncEngine.ts` (≈67, 71, 92, 98) → ключи `sync.*` в i18n.
  ⚠️ Эти строки попадают в **пути папок** — менять только вместе с миграцией/rescan,
  иначе у существующих пользователей появятся папки-дубликаты. Вариант: фиксировать
  строку выбранной локали при создании, не переводить ретроактивно.
- Имена папок в схемах (`'Книги'`, `'Арки'`, `'Якоря'`, `'Главы'`, `'Страницы'`,
  `'Персонажи'`) — `src/models/schema.ts` (`folder`) и `buildPath`. Та же оговорка
  про существующие пути.
- Шаблоны тел заметок — `src/templates/index.ts` целиком русские. Перевести через
  i18n-ключи (шаблон применяется один раз при создании — безопасно).

## P4 — Качество кода и совместимость с Obsidian API

### 18. `[x]` Уйти с приватных API Obsidian

- `(this.app as any).internalPlugins.getPluginById('global-search')` и
  `(this.app as any).commands.executeCommandById` — `src/views/CardView.ts` (`openTagSearch`, ≈949).
  Замена: `app.workspace.getLeavesOfType('search')` + публичных API мало — минимум
  обернуть в try/catch и фолбэк, задокументировать риск.
- `(this.app as any).setting.open()/openTabById` — `src/views/NavigatorView.ts` (≈215).
  Официального API нет; обернуть в optional chaining + фолбэк (Notice «Откройте
  настройки вручную»). Эти места не пройдут ревью community-каталога — для сабмита
  потребуется либо удалить, либо обосновать.

### 19. `[x]` Поддержка deferred views (Obsidian ≥ 1.7.2)

**Где:** `src/main.ts` — `findScLeaf` (≈184), `refreshAllViews` (≈211).

`leaf.view` может быть `DeferredView`-плейсхолдером. Читать файл вкладки через
`leaf.getViewState().state?.file`, а `refresh?.()` уже опционален — ок, но каст
`(leaf.view as EntityFileView).file` упадёт логически (вернёт undefined → вкладка
не найдётся → задублируется). Использовать `getViewState`.

### 20. `[x]` Включить `strict: true` в tsconfig

Сейчас только `strictNullChecks`; `noImplicitAny` выключен. Включить `strict`,
поправить всплывшие ошибки (ожидаемо немного — кодовая база небольшая).

### 21. `[x]` Зависимости

- `nanoid` перенести из `devDependencies` в `dependencies` (рантайм-зависимость,
  бандлится esbuild — работает, но семантика неверная).
- `"obsidian": "latest"` → зафиксировать (`^1.7.2` или актуальный minAppVersion),
  иначе сборка невоспроизводима.
- `esbuild 0.17.3` (январь 2023) — обновить до актуального.

### 22. `[x]` Гайдлайны Obsidian для UI

- Инлайн-стили → CSS-классы: `spacer.style.flex = '1'`, `chipRow.style.margin = '0'`,
  `inp.style.width = '160px'`, `dot.style.background` (динамический цвет — допустимо
  через CSS-переменную, как уже сделано для `--chip-color`) и т.п. в `CardView`,
  `NavigatorView`, `BoardView`, `GraphView`.
- Заголовки настроек: `containerEl.createEl('h2'/'h3')` → `new Setting(...).setHeading()`
  (`src/settings.ts` ≈65–67, 92).
- `console.log` миграции (`ScenaristStore.load`) → убрать или за debug-флагом.

### 23. `[x]` Цвета и темы

Захардкоженные hex (`#888`, `#4a9eff`, `#7ed321`…) в схемах и вью не адаптируются
к светлой теме. Минимум — проверить контраст в обеих темах; лучше — палитра через
CSS-переменные Obsidian (`--color-red` и т.д.) с маппингом.

### 24. `[x]` Мелочи

- `NODE_COLORS` в GraphView содержит `book`, но `book` нет в `GRAPH_KINDS` — либо
  убрать запись, либо добавить книги в граф (решить продуктово).
- `detectLang` через `window.moment.locale()` — в новых версиях API есть
  `getLanguage()`; добавить как основной путь с фолбэком на moment.
- Смена `rootFolder` в настройках не переносит заметки и не запускает rescan —
  как минимум показать Notice с предложением выполнить «Rescan vault».
- Лайтбокс (`CardView.openLightbox`) вешает keydown на document и оверлей на body —
  снимать при `onClose` вью (сейчас останется, если вью закрыли при открытом лайтбоксе).
